The reported “variable stays null” bug stopped on 18 August. The ticket was filed on the 26th.

Every one of the 17 affected instances ran before a package change on 18 August. Since the 19th the affected path has run 21 times with zero failures. The customer corrected their own BPMN and, because the engine never logged anything, had no way to know it had worked — so they raised a ticket for a symptom that was already gone.

What is still live is a different failure on the same element: a 404 from Microsoft Graph because the email was no longer in the mailbox. That is the one the instance attached to this ticket shows, and it ran through 25 August.

Correction to my earlier read: I flagged MST-9979 (mappings persisted with blank name/type) as prime suspect. The BPMN rules that out — every mapping in this process is well-formed. The real cause was a wrong variable reference on one of three converging paths (§5).

What the BPMN shows

Three separate start paths converge on Activity_AkTBVx, and each writes the same shared variable strEmailId (str_EmailID, scoped to Collaboration_1). The consumer interpolates it into the path: pathParameters = {"id":"=js:(vars.strEmailId)"}.

Path A never failed once in 470 runs. Paths B and C account for all 17. Each start event owns its own response variable — Event_start writes response, Event_W68xBg writes response9 — so a mapping on path B that reads vars.response resolves against a variable that is never set on that path. Null, silently.

The mapping in the BPMN today reads =vars.response9?.id, which is correct, and it works: 21 consecutive successes since 19 August (§6). The version that was live during the failures is not recoverable from the current package, but the cutover in §6 dates the change precisely.

Two outputs share the name str_EmailID; the second writes an element-scoped variable strEmailId3 that nothing reads. That is leftover from someone editing this exact mapping.

MST-9979 is ruled out. That defect persisted mappings with blank name and type. Every mapping in this package carries both. A related note: =vars.response9?.id has no =js: prefix, so it routes to DynamicExpresso rather than JavaScript (StringExtensions.cs:316) — I expected the JS-style ?. to fail there, and the 21 clean runs since the 19th show it does not. Worth knowing.

07

Why nobody could tell

The customer's mapping was wrong, but the platform's handling of that mistake is the real finding. Verified against main.

1

A failed expression becomes null

BpmnDataManager.cs:63-64 · EvaluateStringValue

UnwrapOrIfFail((UnsafeThirdPartyValue?)null). The doc comment states it: “If the expression throws, return null.” The Fin knows the difference between evaluated to null and failed to evaluate — and discards it.
2

The null is written unconditionally

BpmnDataManager.cs:1072 · EvaluateActivityOutputs (:1023)

_variablesScope.SetDatum(…) with no null or failed-eval guard, so a mapping that cannot resolve overwrites its target with null. Because Activity_AkTBVx also writes strEmailId from its own result, the fault-time writeback re-nulls it — which is why retries 2 and 3 fail identically instead of recovering.
3

Nothing is logged

no log · no incident · no ErrorCode

A non-swallowing variant exists and is used elsewhere — EvaluateStringValueWithError, raising ErrorCode.ExpressionEvaluationError — but not on this path.

So the customer got no signal when they broke it, and no signal when they fixed it. They spent days on a mapping typo with nothing to guide them, then filed a ticket about a symptom that had already stopped. That is the cost of the swallow, and it is worth fixing even though this particular customer is now unblocked.

The failure only became visible at all because strEmailId happens to feed an IS path parameter, which throws at IntSvcSendTaskActivities.GetInterpolatedPath (:533-562). Had that null landed in a body field, a script input or a gateway condition, there would be no 400 and no telemetry whatsoever.

10

Next steps

DRI

Tell the customer the null-id bug is already fixed

Their 18 August package change resolved it; 21 clean runs since. Ask them to confirm they have seen no null str_EmailID since — and explain the platform gave them no confirmation, which is why they raised it. Close that half of the ticket.
DRI

Reframe the ticket around the 404

That is the live failure and the one df497399 actually shows. Raise the folder-move hazard: the process moves messages five times and Graph message ids change on move, so a stale str_EmailID will 404. Recommend re-reading the id from each move's response rather than carrying the trigger's.
Engine

File the silent-null-write bug

This case is the argument for it: a customer lost days to a mapping typo with zero diagnostics, and got no signal when they fixed it. Skip the scope write when evaluation failed as distinct from evaluating to null — the Fin already carries that and discards it. At minimum log at the swallow point. V1 [Workflow]-reachable and changes evaluated variable state on replay, so it needs /nde-check and likely a Workflow.Patched gate.
Design

Warn on cross-element variable references

Three start paths writing one shared variable, each from its own element-scoped response, is a trap the designer could catch statically: a mapping on element X whose source reads vars.<var owned by element Y> is almost always a copy-paste error. Cheaper than any runtime fix.
Triage

Fold in the existing reports

MST-12996 / MST-12995 (“Global variable becomes null”) and MST-12934 are plausibly the same sink. One owner, not one ticket per customer.

Reproducing the queries

Cluster argus-prd-shared-adx.westeurope, database telemetry, subscription ac48534c-8b8d-4bdf-b523-a09d0fb1b77d. Time columns differ: _raw_Log uses Timestamp, _raw_Trace uses StartTime.

KQL used for this investigation

Find the clobbered variable — the entry point for this bug class

_raw_Log
| where Timestamp > ago(30d)
| where Body has "<tenantId>" and Body has "has null or empty value"
| extend Inst  = extract(@"InstanceId: ([a-f0-9-]{36})", 1, Body),
         Param = extract(@"Parameter .([A-Za-z0-9_]+). has null", 1, Body)
| summarize Hits=count(), First=min(Timestamp), Last=max(Timestamp) by Inst, Param
| order by First desc

Attribute failures to a start path — the decisive query

_raw_Log
| where Timestamp between (datetime(2026-08-10) .. datetime(2026-08-19))
| where Body has "Element completed or failed"
| extend Inst = extract(@"processInstanceId:([a-f0-9-]{36})", 1, Body),
         Elem = extract(@"elementId:([A-Za-z0-9_]+)", 1, Body),
         RC   = extract(@"resultCode:([0-9]+)", 1, Body)
| where Inst in (<the null-id instance ids>)
| summarize Elems=make_set(strcat(Elem,":",RC)) by Inst

Date the package change — per-day outcome on one path

let w68 = _raw_Log | where Timestamp > ago(30d)
| where Body has "Element completed or failed" and Body has "elementId:Event_W68xBg"
| extend Inst = extract(@"processInstanceId:([a-f0-9-]{36})", 1, Body)
| summarize Started=min(Timestamp) by Inst;
let ak = _raw_Log | where Timestamp > ago(30d)
| where Body has "Element completed or failed" and Body has "elementId:Activity_AkTBVx"
| extend Inst = extract(@"processInstanceId:([a-f0-9-]{36})", 1, Body),
         RC   = extract(@"resultCode:([0-9]+)", 1, Body)
| summarize AkRC=make_set(RC) by Inst;
w68 | join kind=leftouter ak on Inst
| extend Day=format_datetime(Started,"MM-dd")
| summarize Runs=count(), Outcomes=make_set(AkRC) by Day | order by Day asc

Incidents by error code

_raw_Log
| where Timestamp > ago(30d)
| where Body has "<tenantId>" and Body has "has been created for the element"
| extend Elem = extract(@"for the element ([A-Za-z0-9_]+)", 1, Body),
         EC   = extract(@"ErrorCode: ([A-Za-z0-9_]+)", 1, Body)
| summarize Cnt=count(), First=min(Timestamp), Last=max(Timestamp) by Elem, EC
| order by Cnt desc
