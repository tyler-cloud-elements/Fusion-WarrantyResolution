### Case-Level SLA Escalation Rules

**Design Rationale:** The case clock carries the PDD §1.2 objective of a 3.5-day mean resolution, set at 4 d so the mean target sits inside the clock; at-risk fires at 70% (2.8 d) because a 3–10 day SLA warns at 70%, giving Global Warranty Operations a day of runway before the objective is missed. Breach escalates one tier to Warranty Leadership because the accountable coordinator is already the at-risk recipient. No interrupting secondary stage is entered through `sla-status-change`: the PDD defines reminder, timer, and escalation *visibility* (BR-003) but no breach work, and PDD §11.4 explicitly defers escalation cadence, so both statuses stay notification-only.

| SLA Status | Threshold | Action | Display Name |
|------------|-----------|--------|--------------|
| At-Risk | 70% of SLA duration | Notify: UserGroup Global Warranty Operations | Warranty Resolution Case SLA at risk |
| Breached | 100% of SLA duration | Notify: UserGroup Warranty Leadership | Warranty Resolution Case SLA breached |

### Variable SLA Rules

**Design Rationale:** PDD §1.2 sets a separate P1 objective — reduce critical line downtime from 96 hours to 24 hours — measured on the same report-to-restored span as the case clock. A condition-based override keeps one case SLA surface while giving P1 outages a 24-hour clock; at-risk fires at 75% (18 h) per the ≤3-day threshold rule, and Field Service is the at-risk recipient because containment and restoration work is theirs during a line-down event.

## Section 2: Stages & Tasks

**Purpose:** The case plan. Every stage has entry/exit conditions, an SLA where the PDD sets a target, and complete task detail blocks. The case has no BPMN-style edges; every transition is expressed by stage entry and exit conditions.

**Routing convention used throughout:** every condition that gates on a human or system decision reads the deciding task's own output field (for example `vars.coverageDecision`), never the case variable that the same task extracts into. A gate is evaluated before the extract lands, so a guard on the extracted variable would read the previous pass. The `->` extract is kept wherever the value must persist for the Case App, a later stage, or the audit trail.

### Stage 1: Intake and impact triage (`s1`)

**Type:** Stage
**Stage Kind:** primary
**Design Rationale:** Primary and first — BR-001 requires a coordination case for every outage report before any WT-9 claim exists, so this stage owns case registration, impact and safety triage, and serial verification. ## Non-Functional Requirements

| Dimension | Requirement / Design decision |
|---|---|
| Security | Least-privilege access per persona — Customer Support acts only at intake, Parts / Logistics only in the substitution lane, Commercial / Legal only after root-case exit. Every connected-system credential belongs to the invoked process or connection, never to the case. Customer contact details and site information are treated as personal data with restricted visibility pending the approved privacy classification (BR-012, SME review item 7). Sentinel Historian telemetry is retrieved only where customer data-sharing permits (PDD §11.2). |
| Performance | 7,400 claims per year — roughly 30 new cases per business day, with a target mean case life of 3.5 days, so expect on the order of 100–200 concurrently open cases plus exception lanes. Every system interaction is an outbound call from a `process` task rather than a long poll; the only inbound waits are the intake event and the post-close signal. |
| Scalability | Human decision tasks are addressed to user groups, never to individuals, so volume spreads across a team — the one place a single recipient would bottleneck every case is route approval, which is why the authority gate resolves to a group at both threshold branches. Coverage and containment run as parallel tracks, so peak load does not serialise. |
| Availability / Resilience | Case state is the recovery point: every stage entry is condition-driven, so a failed process task can be retried without re-running completed work, and `Run Only Once: Yes` protects case registration and terminal outcome records against re-entry. A connected source being unavailable is captured by the optional `Record manual source evidence` task with source ID, time, and manual evidence for later reconciliation (PDD Table 11). **Architect advisory:** the platform emits no connector-failure event, so a genuinely automated failure lane cannot be modelled; if the business wants one, the invoked process must publish a failure signal that a `wait-for-connector` entry can key on. |
| Logging & Monitoring | PDD §9.2 requires timestamps on ownership, stage changes, evidence retrieval, communications, decisions, approvals, restoration validation, cost reconciliation, reopen events, and closure reason — all of which are native case-timeline events here. Written rationale is persisted for coverage (`coverageRationale`), exceptions (`approvedExceptionRationale`), engineering (`engineeringDisposition`), substitution (`substitutionDecision`), and reopen (`reopenReason`). SLA at-risk and breach escalations notify the owner group and one tier up; Case App dashboards carry the §10 KPI set. |
| Compliance | BR-003 is enforced structurally: all seventeen decision points are `action` tasks and no task is typed `agent`, so automation cannot make a coverage, safety, engineering, substitution, restoration, or financial decision. BR-011's interim 10000 threshold is an executable recipient guard on route approval and closure, not documentation. BR-010's single-outcome rule is enforced by one completing case exit plus three mutually exclusive terminal lanes. Retention, privacy classification, telemetry consent, and the audit-evidence standard remain unconfirmed (SME review item 7) and must be settled before go-live. |

## Testing Strategy

| Scenario | Setup | Expected Outcome |
|---|---|---|
| Happy path — repair | T02 fires with a valid serial; impact P3; serial `Verified`; coverage `Approved`; technical route ready; readiness `BothReady`; route `Repair`; validation `Validated`; closure `Close` | Six primary stages complete in order with coverage and containment overlapping; `required-stages-completed` fires; `closureReason` returns "Restored and financially reconciled" |
| Happy path — P1 line down | Same as above with impact `P1` | The P1 case SLA override applies a 24-hour clock; at-risk fires at 18 hours to Field Service; the 4-hour containment clock governs Diagnose and contain |
| Parallel launch | Intake completes with serial `Verified` | Coverage and evidence review and Diagnose and contain are both active simultaneously (BR-002) |
| Unverified serial at intake | Serial verification returns anything other than `Verified` | Intake still completes and containment still starts; the evidence lane enters interrupting; on `Received` it returns to origin, serial verification re-runs, and coverage then enters |
| Evidence incomplete | Coverage decision `EvidenceRequested` | Coverage does not complete; the evidence lane enters; the timer holds a 3-day window in parallel with the human follow-up; on return the coverage decision re-runs |
| Evidence non-response | Evidence follow-up `EscalatedNoResponse` | Escalation is recorded on the case and control returns to the origin stage — no automatic terminal exit, per SME review item 8 |
| Coverage exception | Coverage decision `ExceptionPending` | Coverage completes; the readiness gate opens; `ApprovedException` records rationale and route approval still fires (BR-004) |
| Engineering exception | Diagnosis `EngineeringNeeded` | Diagnose does not complete; the engineering lane enters interrupting; `Approved` or `ReturnForDiagnosis` returns to origin and diagnosis re-runs; `ControlledEscalation` exits to the commercial and legal lane |
| Alternate part | Route `AlternatePart` | Resolution decision does not complete; the substitution lane enters; `Approved` or `Rejected` returns to route approval; `Escalate` exits to the commercial and legal lane |
| Authority threshold | `estimatedClaimCost` = 9,500 then 10,500 | Route approval addresses Field Service in the first case and Warranty Leadership in the second; closure addresses Quality / Reliability then Finance on the reconciled amount |
| Failed validation | Validation `Failed` | Restore and validate does not complete; Diagnose and contain re-enters; a new technical route leads to a new route approval before restoration is retried (BR-008) |
| Terminal — denial | Route `Denial` | Resolution decision does not complete; the denial lane records the notice and sets `closureReason`; the case exits without completing |
| Terminal — withdrawal | Route `Withdrawal` | Withdrawal lane records the outcome; case exits without completing |
| Terminal — commercial or legal | Route `CommercialLegal`, then separately via engineering escalation and via substitution escalation | All three entries reach the handoff lane exactly once each; case exits without completing |
| Quality escalation | Closure disposition `QualityInvestigation` | The quality lane enters off Close and learn's completion and records a disposition without delaying case completion (BR-009) |
| Reopen by decision | Closure decision `Reopen`, target `CoverageReassessment` then `TechnicalReassessment` then `ClosureReassessment` | The reopen lane records the reason; the case re-enters Coverage, Diagnose, or returns to Close and learn respectively, with history preserved |
| Reopen by signal | Post-close signal event delivered while the case is open | The reopen lane enters via `wait-for-connector` exactly once, regardless of which stage was active |
| SLA at-risk and breach | Hold each stage past its at-risk threshold and past 100% | Each configured SLA raises its own at-risk and breach escalation to the mapped recipients; **no** stage or task is created by an SLA, and no `sla-status-change` rule exists to fire |
| Manual start | Start the case through T03 with `manualIntakeReport` populated | Intake tasks read the manual payload where the CRSC payload is empty; the rest of the lifecycle is unchanged |
| Dual-fire guard | Every gated pair — coverage, diagnose, resolution, restore, closure | For each pair, exactly one of completion or divert fires; the guards are exact inverses over the same producing output |
| Reachability | Static review of the emitted plan | Every stage has at least one entry rule with a concrete producer; every decision value on every button is consumed by a downstream rule |
